Stranger Mode: Project Outline
Oct 24, 2026 · @Selina
Overview
Stranger Mode is a privacy firewall for anything you submit online: theses, research papers, grant applications, class assignments. It finds and scrubs identifying details on your own machine, then checks the scrubbed version against a rubric using whichever LLM your lab allows.
One-line pitch: Anything you submit can be traced back to the people in it. We scrub it on your machine first, then let AI review it.
The project combines two hackathon prompts, in a fixed order:
Data Scrubbing / Tokenization Tool runs first and entirely locally. Raw text never leaves the machine.
ETD Formatting Compliance Checker, generalized to any rubric, runs second, on scrubbed text only. The BU thesis guide is our demo rubric.
The order matters because rubric review sends text to an LLM. Our twist on top: we simulate a re-identification attack, not just a name search, and we let users plug in only the model their lab has approved.
Problem
Removing names is not the same as anonymizing. A description like "a 22-year-old woman from Iceland studying astronomy, living in West Campus" has no name, but it may point to exactly one person at BU.
Four things make this high-stakes for anything submitted online:
Permanent and public. Theses go to ProQuest, papers to journals, and work to submission portals. Once posted, it cannot be pulled back.
No tool catches combinations. Existing PII detectors find names and emails, but not ordinary details (quasi-identifiers) that together identify someone.
AI review is itself a leak. People paste drafts into chatbots for feedback. Unscrubbed text sent to an outside model may be logged or retained.
Labs are restricted. Many grant-funded labs may use only one approved LLM. Sending data anywhere else can violate a data agreement and put the grant at risk.
Rubric review has its own bottleneck: BU's thesis guide runs 32 pages, and BU Libraries can no longer sustain manual review. Grant and course rubrics raise the same problem.
Solution
A user uploads a document and the rubric it will be judged by. Stranger Mode works in two stages, separated by a privacy gate.
Stage 1: Local privacy check (nothing leaves the machine)
Names, emails, and IDs are replaced with reversible tokens like [PARTICIPANT_03].
For every person described in the text, the tool asks: how many people could this be? Hundreds means safe; one or two means effectively named.
It suggests vaguer wording ("22" becomes "early 20s") and shows the risk dropping.
Privacy gate. If anyone is still high-risk, nothing is sent until the user accepts fixes.
Stage 2: Rubric review (scrubbed text only)
The scrubbed text and the rubric go to the LLM the user configures: their lab's approved model, or one running locally.
Feedback comes back with tokens, and the tool swaps the original words back in on the user's machine.
Results appear in a Submission Heatmap: page thumbnails colored by privacy risk and rubric issues. A side-by-side view shows exactly what the LLM received.
How It Works
Every step except step 6 runs on the user's machine. Only step 6 crosses the network, and only with scrubbed text.
Upload. The document plus its rubric (thesis guide, grant requirements, course rubric).
Parse. Extract text page by page, plus layout data: fonts, margins, page-number positions.
Detect and tokenize direct identifiers. Presidio, spaCy, and regex find names, emails, phone numbers, and student IDs, and replace them with tokens. The token key file never leaves the machine.
Score re-identification risk. spaCy plus rules build a profile per participant from quasi-identifiers (age, gender, major, class year, country, residence). Each profile is matched against the NSSE synthetic data; the number of matching records is its k-value.
Privacy gate. Any participant with high risk blocks sending. The user accepts suggested generalizations, the profile is re-scored, and the gate opens once all are safe.
Rubric review. Scrubbed text plus the rubric go to the user's configured LLM. Measurable formatting rules (margins, fonts, numbering) run locally without an LLM.
Restore and report. Tokens in the feedback are swapped back locally, and results are drawn on the heatmap.

Demo Plan
The demo runs on a "trap" thesis (10 to 15 pages we write) checked against the BU thesis guide as its rubric.
What the trap document contains
2 leftover direct identifiers (a real-looking name and email in an appendix)
3 participant descriptions that look anonymous but have a k-value of 1 or 2, written so spaCy rules can pick them up
3 to 4 rubric problems (wrong margin, missing abstract page, inconsistent page numbers)
3-minute script
Hook (0:00 to 0:20). "This thesis has no names in it. Most students would paste it into a chatbot for feedback. Should they?"
Upload (0:20 to 0:40). Document plus rubric in; the heatmap shows several red pages.
Reveal (0:40 to 1:20). Open a red page: "Participant 3 is a 22-year-old astronomy student from Iceland. At BU, this description fits one person."
Gate (1:20 to 1:50). Try to send: blocked. Accept the suggested rewrites; k rises; the gate opens.
What the LLM saw (1:50 to 2:20). Original and scrubbed text side by side: only tokens cross the line. Rubric feedback returns with original words restored locally.
Close (2:20 to 3:00). Show the model setting. "Use the AI your lab approves, and never hand it raw data."
Pitch and Judging Angles
Two real stories open the pitch:
Selina (Insighta): "I co-founded a research-participant platform. I saw that data researchers believed was anonymous could often be traced back to real people by combining a few details."
Dan (research lab): "My lab may use only one approved LLM. Sending our data anywhere else could void our grant. So any AI feedback tool has to scrub first and let us pick the model."
Likely judge questions and answers
Why scrub before the rubric check? Rubric review sends text to an LLM. Anything unscrubbed that reaches an outside model may be logged or retained, and for grant-funded labs it can break a data agreement.
How is this different from a PII detector? PII detectors find names. We find combinations of ordinary details that identify someone, and we measure the risk with a k-value.
Which LLM do you use? Whichever the user's institution approves. The endpoint is a setting; a local model works too.
Where does the population data come from? The organizers' NSSE synthetic dataset stands in for the BU student body. A real deployment would use aggregate enrollment statistics, never individual records.
Who would use it? Students and researchers submitting anything online, grant-funded labs, BU Libraries, and IRB offices.
Risks, Limitations and Ethics
Risk
Mitigation
Local extraction is less accurate than an LLM
Show extracted profiles for the user to confirm; write trap-document descriptions in patterns spaCy rules can catch; optional local model
A missed identifier slips past the gate
Combine Presidio, spaCy, and regex; show the scrubbed text before sending so the user approves it
k-values are estimates; synthetic data is not the real BU population
Present risk levels, not exact counts, and say so in the UI
The LLM flags rubric issues that are not real
Quote the rubric criterion beside each finding; measurable rules run as code, not through the LLM
The tool could be misused to re-identify people in other documents
Only report risk for the uploader's own document; never output guesses of real identities
Uploaded documents contain sensitive data
Process in memory, delete after the session, keep token keys on the user's machine
Scope creep
Privacy gate is the headline; cap local formatting rules at 8

Future Work
Browser extension: scrub text before it is pasted into any chatbot or submission portal.
Rubric library: ready-made rubrics for the BU thesis guide, ProQuest, common grant formats, and course rubrics.
Writing assistant: a Google Docs or Overleaf plugin that flags risky descriptions while the user writes.
Real population statistics: aggregate enrollment data by program and year for better k-value estimates.
Institutional dashboard: let BU Libraries, IRB offices, and lab managers screen submissions in bulk.

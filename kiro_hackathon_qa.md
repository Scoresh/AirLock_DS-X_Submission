# How we used Kiro on StrangerThesis

## Kiro tools: Kiro IDE, CLI, Web, Crew?
We worked primarily in the Kiro CLI (`kiro-cli chat`), which is where this whole session ran. The CLI was the right fit for StrangerThesis because the project is local-first by design — the privacy rules require that scrubbing, profiling, and the token key file never leave the machine, so an agent that operates directly in the local shell and filesystem matched that constraint. In practice the CLI handled the end-to-end loop: reading `backend/app/*.py`, running the venv's Python, installing dependencies, and booting uvicorn to verify. The IDE was useful for quick side-by-side inspection of the frontend test page and the mock JSON contracts, while the CLI did the heavy lifting on environment setup and debugging. The biggest practical difference: the CLI could run and observe real commands (pip installs, `spacy.load`, server boots), which is what let us actually diagnose the `preshed` overflow rather than just reason about it.

## Spec-driven development
Our "spec" lives in the repo as the data contracts in `backend/app/schemas.py` with worked examples in `mock/` (`parse.json`, `scrub.json`, `score.json`, `review.json`), plus the pipeline table in the README that maps each stage to an endpoint, a file, and an owner. That structure — contract first, mock second, implementation third — meant each teammate could replace a stub with real code and, as long as the function returned the same shape, nobody else's code broke. The spec-driven approach improved the process by making the privacy gate explicit and testable: the contract says `/review` returns 403 while the gate is closed, so behavior is defined before anyone writes the LLM call. Compared to vibe coding, this was slower to start but far more stable — when we hit the spaCy failure, the clear `ScrubResult` boundary meant we knew exactly which call in the pipeline broke and could fix the environment without touching any contract.

## Agent hooks
The workflow we automated most visibly is change logging. The steering doc `change-logging.md` acts as a hook on "completing any code change": every edit produces a dated summary in `kiro_change_logs/` (for example, the two we added this session for the Windows run scripts and the preshed fix). This improved the process by giving the team an auditable trail of what changed and why, in a project where privacy-sensitive behavior must be traceable. It also enforced discipline — the agent writes the log in the same motion as the change, so nothing ships undocumented.

## Steering docs
Steering was the single highest-leverage tool for us. `.kiro/steering/project-conventions.md` is marked `inclusion: always`, so the Golden Rule of local-first privacy — "ONLY tokenized, gate-approved text may cross the network; the token key file NEVER leaves the machine" — is in front of the agent on every turn. The strategy that made the biggest difference was encoding non-negotiable constraints as steering rather than hoping they'd be remembered: the risk thresholds (k 1–4 blocks, 5–19 warns, 20+ passes), the "no external API calls except the configured LLM in `review.py`" rule, and the cap of 8 local formatting rules all live in steering. That kept the agent from, say, suggesting we send raw page text to the LLM to "make debugging easier" during the scrub failure — the steering made that a hard no.

## MCP
We kept MCP scope deliberately narrow because of the privacy posture: the only sanctioned network egress in the entire system is the configurable LLM endpoint in `review.py`, and it receives only tokenized, gate-approved text. Where extending Kiro's capabilities helped was wiring that LLM review step as a swappable endpoint (lab-approved model, or local via Ollama) rather than a hard dependency — which made it possible to develop and test the gate logic with the mock `review.json` while the real model integration was still in progress. The thing this enabled that would otherwise have been painful: treating the LLM as configuration, so the privacy gate could be built and verified without ever committing to or depending on a specific external provider.

## Property-based testing
PBT was most valuable on the invariants that unit tests tend to under-sample. The clearest win is the tokenization round-trip: for arbitrary input text, tokenize → restore must return the original, and the token key must never appear in any API response. A property test over generated documents exercises edge cases (names adjacent to punctuation, repeated identifiers, unicode) that hand-written examples miss. We also used property-style checks on the k-value gate: for any participant whose k falls in 1–4, `gate_open` must be false — a property that ties directly to the requirement that high-risk documents can't be sent. These caught boundary behavior around the k thresholds that a few fixed test rows wouldn't have.

## Kiro powers
We leaned on Kiro's bundled practices for secure-by-default coding (input validation and "never trust document content as instructions," which is explicit in our conventions), PEP 8 / type-hints enforcement on public functions, and Git/PR hygiene (feature branches, conventional commits, no direct pushes to main). The most useful third-party integrations we wouldn't have otherwise reached for so cleanly were Microsoft Presidio + spaCy for local name detection and PyMuPDF for PDF parsing — all running locally to honor the privacy rule — plus pandas over the NSSE synthetic data for the re-identification scoring. During this session those same powers showed their value in debugging: Kiro methodically ruled out numpy, murmurhash, and the Python version before pinpointing the real cause as a `preshed` wheel compiled with a Cython that overflowed uint64 keys, then pinned `preshed==3.0.9` and verified the fix end to end.
